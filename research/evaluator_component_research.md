## 1. Why This Document Exists

Any system that gives an AI agent persistent memory has to answer one question before
anything else: **given a piece of input, should it be remembered, and if so, as what
kind of memory?** The component that answers this is referred to throughout this
document as the **Evaluator**.

This document consolidates the research and reasoning behind designing an Evaluator
component: the cognitive-science theory it borrows from, the production systems and
papers that have attempted it, a comparison of their approaches, and the design
concepts that generalize beyond any one implementation. It is written so it remains
useful on a future project, even one unrelated to this specific system.

## 2. Theoretical Foundations

### 2.1 Memory taxonomy from cognitive science

AI memory system design borrows almost entirely from human memory research
(Atkinson–Shiffrin, Tulving). The taxonomy that has become standard in AI agent
literature is:

- **Working memory** — the actively held context of the current interaction. In an LLM
  system, this maps to the live context window. It is not "stored" in the traditional
  sense; it simply exists for the duration of the session and either graduates into a
  persistent type or is lost.
- **Episodic memory** — records of specific events, tied to time and context ("the user's
  flight was cancelled on July 20").
- **Semantic memory** — general facts and stable knowledge, detached from *when* they
  were learned ("the user is vegetarian").
- **Procedural memory** — learned rules, skills, or behavioral patterns ("the user
  prefers terse code review comments").

### 2.2 The formalization for AI agents: CoALA

The paper that formalized this taxonomy specifically for LLM-based agents is
**CoALA — Cognitive Architectures for Language Agents** (Princeton, arXiv:2309.02427).
It is the most commonly cited reference point across nearly every memory framework
surveyed below, and is a good starting citation for any future project in this space.

### 2.3 A key structural insight from the literature

A recurring theme across multiple papers (notably PlugMem, arXiv:2603.03296) is that
**semantic and procedural memory are not independent of episodic memory — they are
abstractions derived from it.** Raw experience is captured as episodic memory first;
semantic facts (user preferences) and procedural knowledge (skills, workflows) are
distilled from patterns across many episodic instances. This has a direct design
implication: an Evaluator doesn't strictly need three parallel, independent
classification paths — it can be designed around episodic memory as the base layer,
with semantic and procedural memory partly generated by a separate consolidation
process rather than by real-time classification alone. This document's design chose
real-time classification into all three types for simplicity, but this abstraction
relationship is worth knowing for a more advanced iteration.

## 3. Literature and System Survey

Each entry below is a distinct approach to the "what should be remembered, and as
what" problem, drawn from published papers or documented production frameworks.

### 3.1 Generative Agents (Park et al., Stanford, arXiv:2304.03442)

**Core idea:** No upfront filtering at all. Every observation is written to a single
flat memory stream with an importance score assigned at write time. Periodically, an
LLM-driven **reflection** step reads clusters of recent low-level memories and
synthesizes higher-level insights from them.
**Filtering mechanism:** Happens entirely at *retrieval* time, via a weighted
combination of recency, importance, and relevance — not at write time.
**Takeaway concept:** Importance scoring and reflection/consolidation as separate,
periodic processes rather than a single write-time gate.

### 3.2 MemGPT / Letta (Packer et al., arXiv:2310.08560)

**Core idea:** Treats the LLM's context window as RAM and external storage as disk. The
LLM itself decides, through explicit function/tool calls, when to move information
between tiers.
**Function calls used:** `core_memory_append`, `core_memory_replace`,
`archival_memory_insert`, `archival_memory_search`, `conversation_search`.
**Filtering mechanism:** There is no separate evaluator module — the same model
driving the conversation also decides, via tool selection, what to write and retrieve.
**Takeaway concept:** Self-directed memory management via tool-calling is elegant but
tightly couples the evaluation decision to the conversational model itself, which
trades separation-of-concerns for simplicity.

### 3.3 MemoryBank (Zhong et al., 2024)

**Core idea:** Every memory is assigned a strength score that decays over time
following an Ebbinghaus forgetting-curve model, with continual updating as new
information arrives.
**Filtering mechanism:** Decay-based pruning *after* storage, rather than a
worthiness gate before storage.
**Takeaway concept:** Time-based decay as a substitute for hard deletion — a memory's
influence fades gradually rather than being binary kept/discarded.

### 3.4 Mem0 (Chhikara et al., arXiv:2504.19413)

**Core idea:** A two-stage pipeline — an LLM extracts salient memory candidates from
conversation, then applies adaptive add/update/delete operations based on semantic
similarity matching against existing memory.
**Filtering mechanism:** Extraction (worthiness + content) followed by an explicit
reconciliation step (is this new, a duplicate, or a contradiction of something
already stored).
**Takeaway concept:** This is the closest published approach to a dedicated
"Evaluator" component as designed in this project — extract, then reconcile against
existing state, rather than write-then-decay or model-self-directed.

### 3.5 Zep / Graphiti (Rasmussen et al., arXiv:2501.13956)

**Core idea:** A temporal knowledge graph with three layers — episodic, semantic
entity, and community — using bi-temporal modeling (tracking both when something was
true and when it was recorded) and hybrid multi-strategy reranking at retrieval.
**Filtering mechanism:** Largely structural — most input is ingested into the graph,
and precision comes from entity resolution and graph structure rather than a
reject/accept gate.
**Takeaway concept:** Bi-temporal modeling (event time vs. record time) is a directly
reusable idea — this project's data format design adopted the same distinction
(`event_time` vs. `created_at`).

### 3.6 A-MEM (Xu et al., arXiv:2502.12110)

**Core idea:** Inspired by the Zettelkasten note-taking method — each memory is a
structured "note" that is dynamically linked to other related memories, forming an
evolving associative network.
**Filtering mechanism:** Implicit — a memory's importance emerges from how many
connections it accumulates over time, rather than being scored at write time.
**Takeaway concept:** Associative linking between memories (rather than flat storage)
is a richer retrieval structure, at the cost of significantly more implementation
complexity.

### 3.7 MemoryOS (Kang et al., 2025)

**Core idea:** An operating-system-inspired three-tier storage model — short, medium,
and long-term memory — each tier with its own management strategy.
**Filtering mechanism:** Promotion between tiers over time, rather than a single
accept/reject decision.
**Takeaway concept:** Similar in spirit to treating working memory as something that
"graduates" into persistent memory rather than being classified once and done.

### 3.8 LangMem / LangGraph

**Core idea:** Explicit support for semantic, episodic, and procedural memory types,
including behavior-level (procedural) memory extraction, integrated into the
LangChain/LangGraph ecosystem.
**Known limitation:** Benchmarked with a p95 retrieval latency near 60 seconds on the
LoCoMo benchmark — noted in independent reviews as impractical for live conversational
use, better suited to offline/batch agents.
**Takeaway concept:** A reminder that architectural elegance and production latency
are separate concerns — always check benchmark numbers, not just design descriptions.

## 4. Comparative Analysis

| Approach | Write-time filtering? | Classification mechanism | Conflict handling | Best fit |
|---|---|---|---|---|
| Generative Agents | No | Post-hoc reflection/synthesis | None explicit | Simulation/research agents, not production |
| MemGPT / Letta | Implicit (LLM tool choice) | Self-directed, via prompt | Manual (agent decides via `core_memory_replace`) | Agents needing full autonomy over their own memory |
| MemoryBank | No | N/A (flat store + decay) | None explicit | Systems prioritizing gradual forgetting over hard filtering |
| **Mem0** | **Yes** | **LLM extraction + explicit typing** | **Explicit, similarity-based reconciliation** | **Closest match to a dedicated Evaluator component** |
| Zep / Graphiti | Partial (structural) | Graph/entity-based | Bi-temporal versioning | Agents needing temporal fact-change reasoning |
| A-MEM | No (implicit via linking) | Associative, emergent | Implicit via link density | Research on evolving knowledge networks |
| MemoryOS | Tier-promotion based | Tier-specific rules | Tier-specific | Systems needing graded memory permanence |
| LangMem | Yes | Explicit typed extraction | Basic | Offline/batch agents already on LangGraph |

## 5. Core Design Concepts (Transferable Beyond This Project)

These are the generalizable ideas worth remembering independent of the specific
system being built:

**5.1 Cascade filtering.** Run cheap, deterministic checks (length, blocklist,
stopword ratio, regex pattern match) before invoking an expensive LLM call. This
pattern — cheap filter first, expensive judgment only when needed — applies to almost
any pipeline involving LLM calls at scale, not just memory systems.

**5.2 Atomic decomposition.** A single input can contain multiple independent facts.
Classifying a whole message as one unit risks losing or misclassifying information.
Splitting input into atomic candidate units before evaluating each is a pattern
applicable to information extraction generally, not just memory.

**5.3 Worthiness and classification are separate questions.** Something can be
perfectly classifiable (e.g., clearly episodic in *shape*) while still not being worth
storing (low long-term value). Conflating "what type is this" with "should this be
kept" produces systems that store too much low-value content.

**5.4 Confidence vs. salience are different axes.** Confidence answers "how sure am I
this classification/extraction is correct." Salience answers "how much does this
matter if it is correct." These should never be collapsed into a single score — they
drive different downstream decisions (confidence gates storage; salience drives
retrieval ranking and decay).

**5.5 Redundancy vs. conflict are different failure modes.** A repeated fact is
redundant (reinforce, don't duplicate). A changed fact is a conflict (supersede the
old record, don't just add a new one next to a contradiction). Systems that don't
distinguish these end up either silently duplicating data or silently accumulating
contradictions.

**5.6 Event time vs. record time.** Borrowed directly from Zep's bi-temporal modeling —
when something *happened* and when the system *learned about it* are often different,
and conflating them corrupts any timeline-based reasoning later.

**5.7 Structured output over free-text parsing.** Using schema-validated structured
output (tool-calling / JSON schema) for any LLM-driven classification step is more
reliable than generating free text and parsing it — this generalizes to virtually any
LLM pipeline stage that needs to hand off to deterministic code.

**5.8 Decouple decision logic from infrastructure.** Every serious system surveyed
here — including Mem0 and Zep — treats embedding generation and vector search as
swappable infrastructure, not something bespoke. The actual intellectual contribution
in each of these systems is the decision logic layered on top. This is the same
reasoning applied to this project's own build-vs-reuse decision (documented
separately).

## 6. How This Project's Evaluator Design Maps to the Literature

| Design element in this project | Closest literature precedent |
|---|---|
| Pre-filter before LLM call | General cascade-filtering pattern (not specific to any one paper) |
| Atomic decomposition into candidate units | Not explicitly emphasized in surveyed papers — an original refinement identified as a common gap |
| Worthiness + type + salience + sensitivity scoring | Extends Mem0's extraction step with explicit multi-axis scoring |
| Redundancy vs. conflict check against existing memory | Directly modeled on Mem0's add/update/delete reconciliation |
| `event_time` vs. `created_at` distinction | Directly modeled on Zep's bi-temporal approach |
| Structured JSON decision schema | General best practice, reinforced by every production framework surveyed |
| Reuse embeddings/vector store, own the decision logic | Matches how Mem0, Zep, and Letta are all built in practice |

While researching this topic, a fabricated citation was encountered circulating in a
forum-style page: *"Roberts, Williams & Park (2024), Persistent Memory Architectures
for Autonomous Language Agents, ACL 2024."* It does not appear in ACL proceedings and
its DOI does not resolve — it does not exist. It is recorded here as a caution: when
building a literature base for any project, verify that a cited paper is retrievable
from its actual source (arXiv, ACL Anthology, publisher page) before relying on it,
rather than trusting a summary or forum post that cites it convincingly.

## 8. Glossary

- **Evaluator** — the component that decides whether input should be stored, as what
  memory type, and with what metadata.
- **Salience** — a score representing how important a memory is, independent of how
  confident the system is that the extraction/classification is correct.
- **Consolidation** — the process of synthesizing lower-level memories (typically
  episodic) into higher-level ones (typically semantic or procedural).
- **Bi-temporal modeling** — tracking both when something was true in the world and
  when the system recorded it.
- **Cascade filtering** — running cheap checks before expensive ones so costly
  operations (like LLM calls) only run on inputs that survive earlier, cheaper stages.
- **Structured output** — LLM output constrained to a validated schema (via tool
  calling or JSON schema), rather than free text requiring separate parsing.
